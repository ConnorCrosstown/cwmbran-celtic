Security 4 findings · fix first

These are not theoretical. The combination in SEC‑1 is the specific pattern automated WordPress attacks look for, and the site currently presents all three halves of it.

SEC-1

An account called admin is publicly discoverable, and XML-RPC will let an attacker guess its password hundreds of times per request

Critical

Three separate weaknesses that are minor alone and serious together. The username is discoverable, the login can be attacked in bulk, and bulk attacks bypass the per-request rate limiting that normally protects wp-login.php.

GET /wp-json/wp/v2/users → 200, lists 2 users: "admin", "Malcolm Jarrett" GET /?author=1 → 301 to /author/admin/ POST /xmlrpc.php system.listMethods → system.multicall wp.getUsersBlogs metaWeblog.getUsersBlogs blogger.getUsersBlogs

system.multicall wrapped around wp.getUsersBlogs is the standard amplified credential-stuffing technique: several hundred password attempts inside a single HTTP request, so login-attempt limiters that count requests never trigger.

FixDisable XML-RPC entirely (add_filter('xmlrpc_enabled','__return_false') plus a server-level block on the file — the filter alone still allows the endpoint to be reached). Create a new administrator under a non-obvious name, move content ownership to it, and delete admin. Restrict /wp-json/wp/v2/users to logged-in requests. Add a login-attempt limiter.
SEC-2

The site can be used as a weapon against other people

High

The same XML-RPC endpoint exposes pingback.ping. That method makes the server fetch any URL an anonymous caller names, which turns the site into a traffic reflector against a third party and lets an outsider probe hosts the server can reach but the public cannot.

This matters reputationally as much as technically: the club's server showing up in someone else's attack logs is a hosting-provider conversation nobody wants.

FixSame fix as SEC-1 — turning XML-RPC off closes this too. Nothing on the site uses it; it exists for desktop blogging clients and the Jetpack app.
SEC-3

Exact software versions are advertised in the page source

Medium
<meta name="generator" content="WordPress 7.0.4"> <meta name="generator" content="SportsPress 2.7.31"> <link rel="EditURI" href="https://www.cwmbranceltic.com/xmlrpc.php?rsd">

Scanners use these to shortlist targets: when a vulnerability lands in a given plugin version, sites publishing that version get hit first. The RSD link also advertises the XML-RPC endpoint from SEC-1.

FixFour remove_action lines in inc/hardening.php, which already exists for exactly this kind of thing but currently only handles capabilities.
SEC-4

No security response headers at all

Medium

No Strict-Transport-Security, X-Content-Type-Options, Referrer-Policy, X-Frame-Options or Permissions-Policy. None of these is urgent on its own; together they are the baseline any security review will ask for, and they cost one filter or a Bunny CDN edge rule.

FixAdd them at the CDN edge rather than in PHP, so they apply to static assets too.

Redundant systems 10 findings · your hunch was right

You suspected there was dead weight on the back end. There is more than expected, and one item is an entire second website.

RED-1

A complete duplicate of the club website is live on Vercel, and it invites Google to index it

Critical

cwmbran-celtic.vercel.app still serves the original Next.js build — around twenty pages including home, teams, news, tickets, players, sponsors, shop, programme, gallery and away-days. It duplicates the real site almost page for page. Only one route on it is actually used: /api/feed, which the WordPress feed plugin fetches.

GET https://cwmbran-celtic.vercel.app/ → 200, 65 KB, full homepage GET https://cwmbran-celtic.vercel.app/robots.txt User-Agent: * Allow: / ← crawlable Sitemap: .../sitemap.xml ← and advertised no <meta name="robots" content="noindex"> anywhere

So there are two public "official" Cwmbran Celtic websites competing for the same search results, and the wrong one is fully open to crawlers. Anyone who finds it sees fixtures and news that are no longer being maintained.

FixKeep the deployment (the feed depends on it), but make it invisible: Disallow: / in robots.txt, an X-Robots-Tag: noindex header in next.config.ts, and ideally remove the page routes so only /api/feed remains. Then request removal of any indexed URLs in Search Console.
RED-2

WP Event Manager holds zero events and loads on all 51 pages

Quick win
GET /wp-json/wp/v2/event_listing?per_page=1 → X-WP-Total: 0 Loaded on every page regardless: frontend.min.css 149 KB wpem-grid.min.css, fonts/style.css, jquery-ui.css, timepicker.css common.min.js, jquery-ui core.min.js, jquery.timepicker.min.js

Not a single event has ever been created. The plugin is pure overhead — roughly 200 KB of CSS and JavaScript, plus a jQuery UI dependency, on every page view.

FixDeactivate and delete. Nothing references it. This is the single cleanest win in the audit.

RED-4

The Divi dequeue in functions.php isn't working — it names handles Divi no longer uses

High

The theme deliberately strips Divi's assets on bespoke templates so its own design isn't fighting them. On the homepage, which is in that list, Divi's payload is all still present:

divi-dynamic-critical-inline-css 182,745 bytes (inline, render-blocking) divi-style-parent-inline-inline 26,746 bytes (inline) et-divi-dynamic-tb-1866-tb-2581-1353.css (external) divi-style-css (still enqueued despite being named in the dequeue list)

Divi 4.27's dynamic-assets system emits handles that didn't exist when the dequeue list was written, so the list mostly misses. That 182 KB of inline CSS is the single biggest reason every page's HTML has a ~180 KB floor.

FixRe-derive the handle list from what Divi 4.27 actually enqueues (dump $wp_styles->queue on a bespoke template), and add a guard so a future Divi update that renames them again is visible rather than silent.
RED-5

The theme stylesheet is downloaded twice on every page

Quick win
<link id='divi-style-css' href='.../cwmbran-celtic-2025/style.css?ver=1787323458'> <link id='cc25-css' href='.../cwmbran-celtic-2025/style.css?ver=1787323458'>

Divi enqueues the child theme's style.css automatically, and functions.php enqueues the same file again under its own handle. 160 KB of CSS parsed twice. The browser will reuse the cached bytes, but it still parses both link tags.

FixDrop the cc25 enqueue and rely on Divi's, or keep cc25 and dequeue divi-style — but only after RED-4, since right now that dequeue doesn't fire.

PERF-2

Browser caching is switched off for every static asset

High
GET /wp-content/themes/cwmbran-celtic-2025/style.css cache-control: public, max-age=0, s-maxage=2592000 ↑ browser: never ↑ CDN: 30 days

Bunny CDN caches for thirty days, but max-age=0 tells the visitor's browser to keep nothing. Every repeat visit re-validates all 74 assets — on a phone on mobile data at a ground, that is the difference between instant and sluggish.

The theme already version-stamps its assets by file modification time, so a long cache is completely safe: changing a file changes its URL.

FixAn edge rule for /wp-content/themes/ and /wp-includes/ setting max-age=31536000, immutable. Leave HTML as it is.
PERF-3

Every page carries a ~180 KB HTML floor before any of its own content

High
Homepage HTML 347,782 bytes (59 KB gzipped) inline CSS 226,017 bytes ← 65% of the document inline JS 25,117 bytes 17 stylesheets · 16 scripts · 3.45 MB of assets · 74 requests

Gzip means the transfer is a reasonable 59 KB, so this is not a bandwidth problem — it is a main-thread problem. The browser still has to parse a quarter of a megabyte of CSS before it can paint, on every page, most of it Divi's (RED-4).

FixMostly falls out of RED-2, RED-3 and RED-4. Fix those and re-measure before doing anything more invasive.

Quick win

PERF-5

Admin-only and legacy scripts on public pages

Medium

Analytics accounts for 445 KB via gtag.js — correctly async and non-blocking, and a single property, so no double-counting, but worth knowing it is the largest single script on the site.

Low

Worth stating precisely because it is much smaller than it first looks. Of 243 images on the fixtures page, every single one carries explicit dimensions — the crest helpers set inline width and height, which is exactly right. Only the four kit shots and two others on the homepage lack them.

FixAdd width and height to the kit images in the Music Shirts template. Small, but it removes a visible jump on a slow connection.

Correctness & traps 5 findings

Things that are wrong, or that will go wrong quietly the next time somebody touches them.

FIX-1

Adding one fixture in the admin silently deletes that team's entire published season

Critical

The merge between admin fixture records and the hardcoded lists replaces per team, not per game:

function cc25_fx_merge_lists($static, $rows) { foreach ($static as $team => $data) { if (!empty($rows[$team])) $static[$team]['list'] = $rows[$team]; } ↑ one record replaces the WHOLE list return $static; }

So if somebody adds a single rearranged Reserves game through the admin screen, the other 26 Reserves fixtures vanish from the website. Nothing errors, nothing warns; the page just renders one fixture and looks fine. This is the most dangerous behaviour in the codebase because the failure is invisible and the action that triggers it is one a volunteer would reasonably take.

FixMerge by game key (team|date|opponent) so a record overrides its own fixture and nothing else, or refuse to substitute unless the team is marked fully migrated. The importer is already idempotent and safe, so the migration path itself is sound — it is only this merge rule that is wrong.
FIX-2

Two menu items do nothing when you're already on the fixtures page

High

The Women's Reserves and Women's Under-19s menu items link to /fixtures/#womens_res and #womens_u19. Arriving fresh, that works — the switcher reads the hash on load. But a same-page hash change does not reload the document, and there is no hashchange listener:

assets/premium.js:219 if (document.querySelector('.teamsel button[data-team]')) { var _h = (location.hash || '').replace('#',''); if (_h) switchTeam(_h); // runs once, on load only }

So from /fixtures/#womens, clicking "Women's Under-19s" in the menu changes the URL and nothing else. Two of the seven teams are effectively unreachable from the menu once you're on the page.

FixAdd a hashchange listener calling the same switchTeam, and scroll the section into view.
FIX-3

robots.txt still carries the previous agency's settings and no sitemap

High
# Installed by Nettl User-agent: * Crawl-delay: 300 ← 5 minutes between requests ← and no Sitemap: line at all /sitemap.xml → 301 /sitemap_index.xml → 404 /wp-sitemap.xml → 200 (works, but nothing points at it)

Google ignores Crawl-delay, but Bing and others honour it. At five minutes a page, crawling the site's ~230 URLs takes about nineteen hours — so a Saturday result may not be indexed until Sunday night. There is a working sitemap, but robots.txt never mentions it.

FixRemove the Crawl-delay line and add Sitemap: https://www.cwmbranceltic.com/wp-sitemap.xml. Two lines, and probably the highest-value-per-keystroke fix in the whole audit.
FIX-4

Every page has two canonical tags

Medium
<link rel="canonical" href="https://www.cwmbranceltic.com/"> ← inc/seo.php:170 <link rel="canonical" href="https://www.cwmbranceltic.com/" /> ← WordPress core

They agree on the homepage, so nothing is broken today. But the theme sets a deliberately different canonical on match-report pages so each game gets its own URL — and on those pages a second, competing tag from core defeats the point. Search engines faced with two canonicals may disregard both.

FixOne line: remove_action('wp_head','rel_canonical') in inc/seo.php, since the theme is emitting its own.
FIX-5

Men's results rows can't show a programme link

Low

Carried over from this week's work. Every other team's results rows can show a Programme button; the men's cannot, because that row is itself a single <a> to the match report and a link inside a link is invalid HTML.

FixMove the men's results panel onto the shared cc25_render_static_results renderer, which already handles this properly. Costs the whole-row click, gains consistency and the missing button.

Interface & content 7 findings · plus what to keep

High
Homepage call-to-action buttons: "Buy Matchday Ticket" "Buy a Matchday Ticket" "Buy Tickets" (and again in the main menu)

UX-6

The stylesheet grows by appending, and now overrides itself

FixNot urgent, and not a rewrite. Next time you touch the nav or the Music Shirts styles, consolidate that component's rules into one place and delete the superseded blocks. There is also dead CSS to remove — a "Squad grid (SportsPress players)" section for a grid the theme now renders itself.
UX-7

functions.php is 2,963 lines doing everything

Low

The inc/ directory shows the right instinct — fixtures, sponsors, people, SEO, programmes, COMET and more are all properly separated. But the main file still holds asset loading, the feed helpers, crest resolution, fixture and results rendering, the kit launch data, season match records and 132 hardcoded fixtures.

FixMove the obvious blocks out as you touch them — crests, rendering, kit launch. No big refactor; just stop adding to it.
UX-8

What's genuinely good, and worth not breaking

Keep

Worth recording so it survives the next round of changes: alt text on every image checked; a working skip link; one <main>; heading order that never skips a level; lang="en-GB"; self-hosted Oswald and Inter with font-display: swap; 24 of 28 theme images lazy-loaded; assets version-stamped by modification time; structured data emitting SportsTeam plus a SportsEvent per fixture; the crest helpers setting explicit dimensions so the fixtures page has effectively no layout shift; a health-check screen; and 692 tests across 17 files, all passing.

The feed plugin deserves a specific mention: it refuses to overwrite good cached data with an empty response, and holds 26 hours of cache so a missed cron still serves last-known-good. That is a careful piece of engineering.
